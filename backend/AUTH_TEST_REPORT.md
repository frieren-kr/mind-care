# 로그인 기능 테스트 방법 및 결과

## 1. 테스트 재현 방법

### 1-1. 개발 환경과 DB 준비

프로젝트의 `backend/` 디렉터리에서 Python 환경을 활성화하고 실행한다.
기존 `.env`의 DB 연결 설정을 사용한다.

```bash
python -m pip install -r requirements.txt
docker compose up -d
```

서비스 DB에 001~010이 적용되어 있고 011이 아직 없다면 다음 명령으로 인증 테이블을 생성한다.
기존 볼륨에서는 `docker compose up -d`만으로 새 마이그레이션이 적용되지 않는다.

```bash
docker exec -i mindcare-db psql -U mindcare -d mindcare -v ON_ERROR_STOP=1 --single-transaction < app/db/migrations/011_authentication.sql
```

### 1-2. 테스트 계정 준비

개발용 프로필 시드를 사용하는 환경의 이메일은 `dev-seed-1@example.com`부터
`dev-seed-4@example.com`까지다. 기존 계정에 인증 정보가 없다면 아래 명령으로
12~128자 비밀번호를 직접 설정한다.

```bash
python -m scripts.seed_dev_auth --all-dev-profiles
```

이 명령은 기존 계정에 인증 정보를 연결하며 새 사용자를 생성하지 않는다.
이미 비밀번호를 설정한 계정은 기존 값을 사용한다. 고정 비밀번호를 문서에 기록하지 않는다.
계정 자체가 없는 환경은 [서버 준비 안내](AUTH_CHECK.md#1-서버-준비)를 참고한다.

### 1-3. 서명 키와 로그인 만료 시간 설정

서명 키가 없다면 아래 명령으로 생성한다.

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

출력된 값을 `backend/.env`의 `AUTH_JWT_SECRET`에 넣고 로그인 만료 시간을 설정한다.
기존 설정이 있으면 중복 추가하지 않고 해당 값을 수정한다.

```dotenv
AUTH_JWT_SECRET=<직접 생성한 비밀키>
AUTH_ACCESS_TOKEN_MINUTES=15
```

`AUTH_ACCESS_TOKEN_MINUTES`는 **1~60분 사이에서 조절**할 수 있고 기본값은 15분이다.
예를 들어 `AUTH_ACCESS_TOKEN_MINUTES=60`으로 설정하면 로그인 시점부터 최대 60분간 유효하다.
사용하거나 새로고침해도 만료 시각은 연장되지 않는다. 만료 후 다음 보호 API 요청은 401을 반환한다.

설정 변경은 **서버를 재시작한 뒤 새로 로그인해 발급받는 토큰**에 적용된다.
기존 토큰의 만료 시각은 바뀌지 않는다. 서명 키는 서버의 토큰 발급·검증용 비밀값으로,
로그인 비밀번호와 다르며 만료 시간마다 새로 생성할 필요가 없다.

### 1-4. 서버 실행

```bash
PRELOAD_EMBEDDING_MODEL=0 python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

이미 서버가 실행 중이라면 종료 후 재시작한다. 기존 서버가 같은 포트를 사용 중인 상태에서
두 번째 서버를 띄우지 않는다.

### 1-5. 로그인 흐름 점검

다른 터미널의 `backend/` 디렉터리에서 실행한다.

```bash
python -m scripts.check_auth --base-url http://127.0.0.1:8000
```

이메일에 `dev-seed-1@example.com`, 비밀번호에 직접 설정한 값을 입력한다.
로그인·내 정보·본인 프로필·설정 조회는 200, 미인증 요청은 401,
다른 사용자 경로는 403, 로그아웃 이후 기존 토큰 사용은 401이어야 한다.
점검 스크립트는 비밀번호·토큰을 출력하지 않고, 이번에 만든 세션을 폐기한다.

추천 응답까지 점검하려면 `--recommendations`를 추가한다. 이 경우 실제 검색·LLM이 실행될 수 있다.
수동 API 호출은 [Swagger 확인 방법](AUTH_CHECK.md#2-swagger로-확인)을 참고한다.

### 1-6. 자동 테스트 실행

[자동 테스트 실행 방법](AUTH_CHECK.md#4-자동-테스트)에 있는 두 명령으로
오프라인·회귀 테스트와 PostgreSQL 통합 테스트를 실행한다.
DB 테스트는 격리 스키마에서 수행하고 롤백하므로 서비스 DB에 계정이나 비밀번호를 남기지 않는다.

## 2. 검증 개요

- 확인일: 2026-11-02
- 대상: 기존 계정 로그인·내 정보·현재 세션 로그아웃·개인화 API 접근 권한
- 결과: 관련 자동 테스트 **91개 통과**, 실행 중인 서버 기본 점검 **10개 통과**
- 실행 가이드: [AUTH_CHECK.md](AUTH_CHECK.md)
- API 계약: [docs/api.md](../docs/api.md), DB 계약: [docs/db.md](../docs/db.md)

이 결과는 현재 작업본을 검증한 기록이다. GitHub push 또는 배포 완료를 뜻하지 않는다.
자동 테스트 결과는 구현 시 실행 기록을 기준으로 하며, 실제 서버 결과는 사용자가 공유한
`scripts.check_auth` 실행 출력으로 확인했다. 이 문서 작성만을 위해 테스트를 다시 실행하지는 않았다.

## 3. 확인한 기능

| 기능 | 동작 |
|---|---|
| `POST /auth/login` | 이메일·비밀번호 검증 후 액세스 토큰과 사용자 정보 반환 |
| `GET /auth/me` | 토큰 서명과 DB 세션 상태를 확인한 뒤 현재 사용자 반환 |
| `POST /auth/logout` | 현재 로그인 세션만 폐기. 해당 토큰은 이후 보호 요청에서 거부 |
| 사용자·환자 조회 | 로그인 사용자와 경로의 사용자 ID 비교, 담당 환자 관계 확인 |
| 피드 설정 조회·변경 | 본인만 허용 |
| 추천 API | 인증·본인 확인 후 개인화 데이터 조회 및 실행기 초기화 |

보호 경로는 `/feed/{user_id}`, `/feed_user/{user_id}`, `/feed_patient/{user_id}/{patient_id}`,
`/recommendations/{user_id}`, `GET/PATCH /users/{user_id}/feed-settings`다.
`/health`와 일반 논문 조회는 공개 상태를 유지한다.

## 4. 자동 테스트 결과

| 테스트 파일 또는 범위 | 개수 | 주요 확인 사항 | 결과 |
|---|---:|---|---|
| [test_auth_security.py](tests/test_auth_security.py) | 6 | 비밀번호 해시·공백 보존, JWT 서명·알고리즘·필수 항목, 만료 경계, 키 누락 | 통과 |
| [test_auth_api.py](tests/test_auth_api.py) | 15 | 로그인·내 정보·로그아웃, 권한 차단, 입력값 보호, 요청 제한, DB 오류, 공개 경로 유지 | 통과 |
| [test_auth_db.py](tests/test_auth_db.py) | 10 | 실제 DB 로그인 흐름, 세션 소유·만료·폐기, 계정 상태, FK·이메일 중복, 점검 스크립트 | 통과 |
| [test_seed_dev_auth.py](tests/test_seed_dev_auth.py) | 14 | 기존 계정 인증 정보 연결, 프로필 보존, 중복 실행·롤백, 비활성 계정, 개발 환경 제한 | 통과 |
| 관련 피드 설정·추천·캐시·실행기·CORS 회귀 테스트 | 46 | 기존 업무 동작 및 DB 제약 유지 | 통과 |
| **합계** | **91** | 오프라인·회귀 56개 + 실제 DB 통합 35개 | **통과** |

실행 명령과 회귀 테스트의 정확한 클래스 목록은 [자동 테스트 실행 방법](AUTH_CHECK.md#4-자동-테스트)을 따른다.
91개는 관련 범위의 테스트 수이며, 저장소 전체 테스트를 실행한 결과는 아니다.

- 인증 테스트는 실제 암호 검증·인증 의존성을 실행한다. 기존 업무 회귀 테스트만 인증 의존성을 대체한다.
- 미인증·타인 경로 요청은 응답 코드뿐 아니라 개인화 조회·설정 변경·AI 실행기 초기화의 미호출을 검증한다.
- DB 테스트는 격리 스키마에서 실행하고 롤백한다. 이 테스트를 통과해도 실제 서비스 DB에
  인증 테이블이나 테스트 계정 비밀번호가 자동으로 남지는 않는다.
- 만료 검증은 시각을 고정하거나 기준 시각을 전달해 수행한다. 실제 서버에서 15분을 기다린 검증은 아니다.

## 5. 실제 서버 점검 결과

서버 자체에서 아래 명령을 실행한 사용자 제공 로그를 기준으로 한다.

```bash
cd /data/mind-care/backend
python -m scripts.check_auth --base-url http://127.0.0.1:8000
```

사용 계정: `dev-seed-1@example.com`. 실제 비밀번호·토큰·서명 키는 기록하지 않는다.

| 순서 | 점검 항목 | 기대 HTTP | 실제 HTTP | 결과 |
|---|---|---:|---:|---|
| 1 | 로그인 | 200 | 200 | 통과 |
| 2 | 내 정보 | 200 | 200 | 통과 |
| 3 | 본인 프로필 | 200 | 200 | 통과 |
| 4 | 본인 피드 설정 조회 | 200 | 200 | 통과 |
| 5 | 토큰 없는 접근 차단 | 401 | 401 | 통과 |
| 6 | 다른 사용자 경로 차단 | 403 | 403 | 통과 |
| 7 | 다른 사용자 설정 변경 차단 | 403 | 403 | 통과 |
| 8 | 로그아웃 | 200 | 200 | 통과 |
| 9 | 로그아웃한 토큰 차단 | 401 | 401 | 통과 |
| 10 | 로그아웃 반복 호출 | 200 | 200 | 통과 |

점검이 만든 세션은 폐기했고 기존 프로필·설정은 변경하지 않았다.
다른 사용자 경로는 스크립트가 생성한 임의 UUID다. 실제 다른 계정의 존재 여부와 관계없이
본인 ID가 아닌 경로를 403으로 차단하는 것을 확인한다.

이 실행에서는 `--recommendations` 옵션을 사용하지 않았다.
실제 논문 추천·외부 LLM 호출·브라우저 및 모바일 프론트 연결은 이 서버 점검의 검증 범위가 아니다.
