### 4.2 DB 구조

기존 `users.id` 및 환자·추천 데이터의 연결은 유지한다. 인증 정보는 응답 모델에 섞이지 않도록 별도 테이블로 분리하는 안을 제안한다.

| 테이블 | 주요 컬럼 | 목적 |
|---|---|---|
| `user_credentials` | `user_id` PK/FK, `password_hash`, `is_active`, `password_changed_at` | 비밀번호 검증 및 계정 사용 여부 |
| `auth_sessions` | `id`, `user_id`, `created_at`, `expires_at`, `revoked_at` | 로그인 1회에 대응하는 세션 |
| `auth_refresh_tokens` | `id`, `session_id`, `token_hash` UNIQUE, `created_at`, `expires_at`, `used_at`, `revoked_at` | 현재·이전 갱신 토큰 추적 및 재사용 감지 |

- 기존 사용자에게 인증 정보가 없으면 로그인할 수 없도록 한다. 사용자 데이터 자체는 삭제하지 않는다.
- 이메일은 기존 `normalize_email()` 정책을 재사용한다. 기존 데이터의 정규화 충돌 여부를 검사하고, DB 유일성 제약으로 동시 가입도 방어한다.
- 비밀번호는 Argon2id 등 전용 해시로 저장한다. 암호화 후 복호화하는 방식이나 일반 SHA 해시를 사용하지 않는다.
- 갱신 토큰은 충분히 무작위인 불투명 토큰으로 발급하고 DB에는 해시만 저장한다. 비밀번호와 달리 높은 엔트로피의 무작위 토큰에는 SHA-256 같은 해시를 사용할 수 있다.
- 과거 갱신 토큰은 재사용 감지가 필요한 기간 동안 보관하고, 만료된 세션·토큰의 정리 정책을 정한다.
- 계정 생성과 자격 증명 생성은 하나의 트랜잭션으로 처리한다.
- 현재 `create_user()` 내부 저장 함수는 자체 커넥션을 사용한다. 이를 호출한 뒤 다른 커넥션으로 인증 정보를 저장하면 원자성이 깨지므로, DB 계층에 두 INSERT를 묶는 가입 함수를 추가한다.

### 4.3 API 계약 초안

1차 기본안은 JSON 요청과 Bearer 액세스 토큰이다. 비밀번호 폼 형식의 OAuth2 엔드포인트를 구현한 것으로 문서화하지 않는다.

| API | 요청 | 성공 응답 | 비고 |
|---|---|---|---|
| `POST /auth/register` | 이름·이메일·비밀번호·선택 전화번호 | `201`, 공개 사용자 정보 | 가입 후 로그인 별도 호출 |
| `POST /auth/login` | 이메일·비밀번호 | `200`, 토큰 쌍·만료 정보·공개 사용자 정보 | 새 세션 생성 |
| `GET /auth/me` | Bearer 액세스 토큰 | `200`, 공개 사용자 정보 | 프로필·환자 전체 조회와 구분 |
| `POST /auth/refresh` | `refresh_token` | `200`, 교체된 토큰 쌍·만료 정보 | 만료된 액세스 토큰 없이도 호출 가능 |
| `POST /auth/logout` | `refresh_token` | `200`, `{"ok": true}` | 현재 세션 폐기. 반복 호출도 같은 응답 |

토큰 응답 필드 예시: `access_token`, `refresh_token`, `token_type: "bearer"`, `expires_in`, `refresh_expires_at`. 공개 사용자 정보는 `id`, `name`, `email`, `feed_refresh_days`처럼 필요한 필드만 명시하며 비밀번호 해시·토큰 해시를 포함하지 않는다.

오류 계약:

- `401`: 로그인 실패, 액세스 토큰 누락·만료·변조, 폐기된 세션, 무효한 갱신 토큰. Bearer 인증 실패에는 `WWW-Authenticate: Bearer`를 포함한다.
- `403`: 유효한 로그인 사용자가 다른 `user_id`를 지정함.
- `404`: 본인 확인을 통과했지만 환자가 없거나 본인의 담당 환자가 아님. 다른 환자의 존재 여부를 구분하지 않는다.
- `409`: 가입 이메일·전화번호 등 고유값 충돌. 이메일 중복 노출 정책은 가입 화면 계약과 함께 확정한다.
- `422`: 입력 형식·길이·허용값 오류.
- `429`: 로그인 등의 요청 한도 초과. 재시도 안내를 함께 제공한다.
- `503` 등 서버 오류: DB·인증 저장소 장애. 이를 잘못된 비밀번호나 세션 만료로 바꾸지 않는다.

존재하지 않는 계정, 비밀번호 불일치, 비활성 계정의 로그인 실패 문구는 동일하게 한다. 인증 요청의 Pydantic 오류에는 입력 비밀번호가 포함될 수 있으므로 오류 응답·로그에서 민감한 입력값을 제거한다.

### 4.4 토큰 검증과 로그아웃

- 액세스 JWT에는 최소한 `sub`(사용자 ID), `sid`(세션 ID), `iat`, `exp`, `iss`, `aud`를 넣고 환자 정보나 비밀번호를 넣지 않는다.
- 서버가 허용한 알고리즘·서명·발급자·대상·만료·필수 클레임을 검증한다. 토큰이 지정한 알고리즘을 무조건 신뢰하지 않는다.
- 이 문서의 기본안은 **매 보호 요청마다 세션·계정 상태를 조회**하는 방식이다. JWT의 `sub`와 세션의 사용자도 일치해야 한다.
- 따라서 로그아웃 후에는 이미 발급된 액세스 토큰도 다음 인증 검사에서 거부된다. 이미 인증을 통과해 실행 중인 요청까지 취소하는 기능은 범위 밖이다.
- 인증 저장소 장애 시 개인화 요청을 허용하지 않으며 서버 오류로 처리한다.
- 갱신 시 세션 잠금·조건부 갱신 등을 이용해 기존 토큰 사용 처리와 새 토큰 저장을 같은 트랜잭션에서 수행한다.
- 이미 사용된 갱신 토큰이 재사용되면 해당 세션 전체를 폐기한다. 프론트는 동시에 여러 갱신 요청을 보내지 않아야 한다.
- 재사용 감지에 따른 폐기는 오류를 반환해도 DB에 반영되어야 한다. 트랜잭션 안에서 예외를 던져 폐기 작업까지 롤백하지 않도록 결과 상태를 반환한 뒤 서비스에서 오류로 변환한다.
- 로그아웃은 토큰이 연결된 세션을 폐기하고, 이미 폐기됐거나 알 수 없는 토큰이어도 성공 응답으로 통일한다. 형식 오류는 별도로 검증한다.

### 4.5 기존 API 보호

기존 경로는 유지하고 인증 의존성을 추가한다. `/me` 기반 경로로 일괄 변경하는 작업은 1차 범위에서 제외한다.

| 보호 대상 | 검사 |
|---|---|
| `GET /feed/{user_id}` | 인증 + 본인 |
| `GET /feed_user/{user_id}` | 인증 + 본인 |
| `GET /feed_patient/{user_id}/{patient_id}` | 인증 + 본인 + 담당 환자 |
| `GET /recommendations/{user_id}` | 인증 + 본인 + 선택한 환자의 소유 관계 |
| `GET /users/{user_id}/feed-settings` | 인증 + 본인 |
| `PATCH /users/{user_id}/feed-settings` | 인증 + 본인 |

`/health`와 일반 논문 조회 API는 1차에 공개 상태를 유지하는 안이다. 개인화 API와 별도로 공개 범위를 확정한다.

실행 순서: **토큰 검증 → 세션·계정 확인 → 경로 본인 확인 → 환자 소유 확인 → 개인화 데이터·캐시 조회 및 AI 실행**.

추천 라우터에는 이미 `get_feed_execution` 의존성이 있다. 라우터 본문에서만 본인 확인을 하면 다른 의존성 초기화가 먼저 실행될 수 있으므로, 개인화 조회와 비용이 드는 실행기 초기화가 인증 이후에 이루어지도록 의존성 구조도 점검한다. 인증 실패를 AI 검색 폴백으로 처리하지 않는다.

## 6. 테스트 방식

### 6.1 단위 테스트 — DB·외부 API 없이

예정 파일: `tests/test_auth_security.py`.

- [ ] 같은 비밀번호라도 salt로 인해 해시가 달라지고, 정상 비밀번호만 검증된다.
- [ ] 해시나 API 응답에 원문 비밀번호가 남지 않는다.
- [ ] 정상 JWT 검증에 성공한다.
- [ ] 변조·만료·서명 불일치·허용하지 않는 알고리즘·필수 클레임 누락을 거부한다.
- [ ] 발급자·대상·사용자 UUID·세션 ID의 잘못된 값을 거부한다.
- [ ] 시간은 주입·고정하여 만료 직전·정확한 만료 시각·만료 이후를 검증한다. 실제 대기는 사용하지 않는다.

### 6.2 API 테스트 — TestClient와 DB 함수 대역

예정 파일: `tests/test_auth_api.py`, `tests/test_auth_permissions.py`.

인증 자체를 검증하는 테스트는 실제 인증 의존성과 토큰 검증을 실행하고 DB·외부 서비스만 대체한다. 기존 업무 로직의 회귀 테스트에서는 인증 의존성만 테스트 사용자로 교체할 수 있다.

| 시나리오 | 확인할 결과 |
|---|---|
| 정상 가입·로그인·`/auth/me` | 상태 코드·응답 필드·사용자 일치 |
| 비밀번호 오류·없는 계정·비활성 계정 | 동일한 로그인 실패 응답 |
| 토큰 없음·잘못된 Bearer·만료·변조 | 401, 개인화 업무 함수 미호출 |
| 사용자 A 토큰으로 사용자 B 경로 요청 | 403, B의 데이터 조회·설정 변경·AI 실행 없음 |
| A 본인 경로에서 B의 환자 요청 | 404, 환자 상세 접근 없음 |
| A의 환자·설정·추천 정상 요청 | 기존 응답 형식과 기능 유지 |
| 로그아웃 후 기존 액세스 토큰 사용 | 401 |
| 회원가입 입력·비밀번호 길이 오류 | 422, 오류 본문에 비밀번호 없음 |
| 로그인 횟수 초과 | 429, 지정 시간 경과 후 정상 복구 |
| 인증 저장소 장애 | 서버 오류, 로그인 허용이나 401 오분류 없음 |

권한 테스트는 조회뿐 아니라 `PATCH`도 검증한다. 미인증 요청에서 업무 함수의 `assert_not_called()`를 확인해 데이터 접근과 AI 호출이 실제로 차단되었음을 검증한다.

### 6.3 PostgreSQL 통합 테스트

예정 파일: `tests/test_auth_db.py`.

전용 테스트 DB 또는 고유한 격리 스키마를 사용한다. 실제 FK·UNIQUE·인덱스가 포함된 마이그레이션을 적용하고 종료 시 정리한다. 테이블을 단순 복사해 외래키 등이 빠진 상태로 테스트하지 않는다. 동시성 검증은 서로 다른 커넥션을 사용한다.

- [ ] 마이그레이션 후 기존 사용자·환자·피드 관계가 유지된다.
- [ ] 인증 정보가 없는 기존 계정은 로그인할 수 없다.
- [ ] 인증 정보 저장 실패 시 사용자 INSERT도 롤백된다.
- [ ] 같은 이메일의 동시 가입에서 한 계정만 생성된다.
- [ ] 갱신 성공 후 이전 토큰은 다시 사용할 수 없다.
- [ ] 이전 토큰 재사용 시 해당 세션 전체가 폐기되고, 이 폐기가 오류 응답 후에도 유지된다.
- [ ] 동일 갱신 토큰의 동시 사용에서 유효한 후속 토큰이 여러 개 생기지 않는다. 재사용 감지로 세션이 폐기되는 정책도 확인한다.
- [ ] 한 세션의 폐기가 같은 사용자의 다른 세션까지 폐기하지 않는다.
- [ ] 폐기·만료된 세션과 비활성 계정을 거부한다.
- [ ] 액세스 토큰의 사용자와 세션 소유자가 다르면 거부한다.
- [ ] 갱신해도 세션의 절대 만료 시각이 연장되지 않는다.
- [ ] DB에는 비밀번호·갱신 토큰 원문이 저장되지 않는다.

기존 `test_feed_settings_db.py`의 격리 방식은 참고하되, 별도 커넥션을 여는 인증 함수와 동시성 테스트에서는 하나의 외부 롤백만으로 정리가 끝난다고 가정하지 않는다.

### 6.4 기존 기능 회귀 테스트

- [ ] 피드 갱신 주기 1~7일 검증·저장·프로필 반영이 유지된다.
- [ ] 추천의 AI·검색 폴백과 캐시 동작이 인증된 요청에서 유지된다.
- [ ] 환자 0명인 신규 회원의 프로필·추천이 정상 응답한다.
- [ ] 공개로 유지하기로 한 헬스 체크·논문 조회가 유지된다.
- [ ] 외부 LLM·PubMed·임베딩 모델 다운로드 없이 인증 테스트를 실행한다.
- [ ] 기존 테스트의 없는 사용자 404 기대값을 검토한다. 다른 사용자 경로는 403, 유효한 인증을 만들 수 없는 삭제 계정은 401이 될 수 있다.

### 6.5 실행 명령 예시

아래 신규 테스트 모듈은 **아직 존재하지 않으며 구현 후 사용할 명령**이다. 개발용 실제 계정·운영 DB에 대해 실행하지 않는다.

```bash
cd /data/mind-care/backend

# 신규 오프라인 테스트: 실제 DB·LLM 접근을 차단한 상태
PRELOAD_EMBEDDING_MODEL=0 python -m unittest \
  tests.test_auth_security \
  tests.test_auth_api \
  tests.test_auth_permissions

# DB 통합 테스트: 전용 테스트 DB 연결 설정과 격리 구성을 먼저 준비
PRELOAD_EMBEDDING_MODEL=0 python -m unittest tests.test_auth_db

# 기존 회귀 테스트: 인증 조건 수정 후 실행
# recommendations 등 일부 테스트는 DB가 필요하므로 테스트 DB를 사용
PRELOAD_EMBEDDING_MODEL=0 python -m unittest \
  tests.test_feed_settings \
  tests.test_feed_settings_db \
  tests.test_recommendations \
  tests.test_dev_cors
```

수동 API 확인은 Swagger 또는 HTTP 클라이언트로 테스트 사용자 A·B를 만들어 수행한다. 가입 → 로그인 → `/auth/me` → 본인 프로필·설정·추천 → 타인 경로 차단 → 갱신 → 로그아웃 → 기존 토큰 거부 순서로 확인한다. 비밀번호·발급 토큰은 공유 문서나 셸 기록에 붙여 넣지 않는다.
